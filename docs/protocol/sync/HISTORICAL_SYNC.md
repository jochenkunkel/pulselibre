# Historical BLE sync – offline-first design

## Why
The wearable is not continuously connected. Measurements made while out of Bluetooth range should appear under their original timestamps through the now verified CIRQA historical transfer. The V24/V25 device runs prove successful transfer of the listed files, **not** complete coverage of the device's entire historical archive.

## Contract
- Distinguish measurement timestamp from receive/import timestamp; show last successful sync in UI.
- Store local measurements persistently and transactionally; enforce a stable uniqueness key per device, metric and device-provided sample identifier (or documented timestamp/sample sequence fallback).
- Request history only when a **verified** device protocol supports it. Determine retention limits and whether historical HR, steps, sleep and SpO2 are available independently.
- Idempotent replay: retransmission and repeated reconnects must not create duplicate records.
- Import and sync checkpoint must commit **in the same database transaction**. Never advance cursor for a partial, failed or unpersisted batch.
- On disconnect retain stored data; on reconnect query the gap with overlap, validate packets, deduplicate, and continue.
- Device clock/time-zone drift, daylight-saving transitions, invalid samples, metric-specific sampling intervals and device resets require explicit handling.
- Reconnection must be bounded and battery-aware; Android background BLE restrictions and permissions must be considered. Do not promise guaranteed background sync.
- Never reset/unpair the band or interfere with existing Garmin Connect pairing.

## Implementation state (verified V24/V25/V26, 2026-11-19)
- Verified read-only device sequence: Connect-style `sync_request` (5043/5044), Item-List, PullItem, transfer-handle configuration and MLR data pipe (0x2018).
- V24/V25 transferred 33/33 listed files; V26 transferred 42 listed files (40 FIT, 2 non-FIT; 218,951 B). The V26 listing included 10 FIT contents and one raw content not present in the prior private archive, while one prior FIT was not observed. All received FIT files passed local envelope/CRC checks and all received files were content-addressed by SHA-256.
- In V25 the list was continued **only if `session_id` was present**; `next_transaction_id` was not treated as a page cursor. V25 ended after one page with 33 items. V26 still did not close the completeness gap.
- SQLite has 294 imported observations (`heart_rate=129`, `distance=129`, `speed=36`); V26 replay did not add duplicate normalized observations.
- **Historical device download is not an automatic product feature.** The proven transfer is exercised through the explicitly started Test Laboratory `startSyncRequestTest` path; no startup/background BLE scheduler, durable per-device-UID download ledger, reconnect/resume workflow, or proven incremental skip policy exists. Separately, on app entry a bounded offline worker replays already verified `filesDir/verified_fit` originals through `CirqaFitBackfill` and persists their supported observations in the canonical FIT store, then inventories unknown fields. This local replay performs no BLE operation and is safe to repeat; truncation, file errors, and import errors must not be described as complete history.
- **Incremental transfer is not yet safe to enable:** the observed item UID is available to the parser, but its stability/reuse semantics across listing generations, file replacement, and device retention have not been established. Content SHA-256 is known only after pulling bytes, so it provides idempotent local storage/import but cannot by itself avoid radio transfer.
- A separately gated Test Laboratory case compares two read-only FileAccess item-list responses within one BLE session. Direct list requests without `sync_request` did not receive a list response. The fourth bounded, user-confirmed no-pull probe sent one `sync_request` and received one 45-item FileAccess list page; it stopped before MLR, pull, pagination and import. The fifth, sixth, and seventh runs each compared two lists after one `sync_request`: both lists had 23 items and 23 unchanged UID/metadata pairs, with no changed/added/missing/duplicate UIDs, and zero MLR bytes/chunks or file pulls. This demonstrates repeatability only for those responses in-session; cross-session UID stability and archive completeness remain untested. Before run four, the user may have accidentally pressed the wearable's action button; Garmin Connect reportedly warned and disabled it. This is a plausible but unverified explanation for the earlier 45-vs-23 difference.
- The first two S25 attempts (2026-11-19) each timed out without a FileAccess 5044 response. Both observed a verified GFDI 5000 frame for 5043; that frame can be a transport ACK, not proof of application-level list acceptance. The earlier generic `accepted=false` field reflected the sync-only acceptance flag and was removed from item-list reports. No file pulls or `sync_request` were sent.
- The third direct-list attempt decoded that frame as a successful transport ACK (`requestId=1`, `offset=0`, `successFlag=0`, `status=0`) but still received no 5044 list response. The separate, user-confirmed diagnostic path sent one `sync_request` followed by one Item-List request and received a single page (`items=45`, `session=false`, `nextTransaction=true`, `pullSent=false`, MLR chunks/bytes 0). It stopped before MLR registration, file pulls, pagination, or import. The possible device-side sync marker was disclosed; this does not enable automatic download.
- The two-list no-pull mode compares UIDs/metadata in memory within one BLE session and reports counts only; each run may still cause a device-side transferred marker because it sends `sync_request`. The seventh run consumed the shared S25 budget at 7/15.
- The pure `HistorySync.kt` merge/checkpoint helper is **not** the entire production sync implementation. Do not describe the proven file-store/SQLite import pipeline as absent; do not infer that all intended transactional checkpoint, reconnect, background, retention or history-completeness guarantees are proven.
- Offline `CirqaFitBackfill.run()` returns per-input, ordinal-only aliases with decoded/eligible counts and missing-timestamp/out-of-range/unsupported-field counts. It distinguishes invalid files from valid files with no eligible observations, and marks a pass truncated when cancellation or safety limits prevent scanning the full eligible directory. This summary is in-memory for the invocation; it is not a durable device sync/import-status ledger and contains no filename or content hash.
- A file contributes to the bounded sync path's completed-file count only after exact private raw-file storage, or (for FIT) verified private storage plus successful canonical SQLite commit. A stored FIT whose decode/import fails is retained for offline recovery but is not reported as a completed pipeline file.
- The current sync report separately exposes whether the run queue drained (`runDrained`) and always labels archive coverage `device-history-unverified`. Directory/page/file/byte safety limits stop the run as incomplete rather than silently dropping entries; this does not yet provide cross-connection resume.
- A visible device-screen action starts the user-confirmed historical sync through the existing Connect-compatible 5043/MLR implementation. It uses only the required BLE connect permission, warns that `sync_request` may mark records transferred on-device, and sends no delete/archive/SetFlags/reset/CLOSE_ALL command. This is foreground, user-initiated work, not an automatic background sync.
- The listed files **do not prove** exhaustive history. The non-FIT files are not yet semantically decoded. The current FIT parser supports a restricted set of Record/Monitoring fields; other fields and sleep-related content require the [offline field inventory](https://github.com/jochenkunkel/pulselibre/issues/141).
- The V26 item list also does not prove exhaustive history; the missing prior FIT and limited list page remain unresolved. No further device run, gate reset, archive, flag, delete, or CLOSE_ALL operation is authorized by this document.

## Acceptance tests planned
1. Band out of range for 24h, then reconnect and backfill original timestamps.
2. Same batch delivered twice -> one record per unique sample.
3. Connection loss midway -> no skipped records or prematurely advanced cursor.
4. Process death during transaction -> rollback; safe retry.
5. DST/time-zone changes and clock drift do not silently rewrite measurement times.
6. Missing history on device -> show data gap, never synthesize values.
